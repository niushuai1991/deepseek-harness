# Agent Note: The dsh desktop shell is an Electron window over the web sidecar

Status: implemented

English | [中文](2026-08-14-dsh-desktop-electron-shell.zh.md)

## Problem

The web app's runtime shape — a loopback HTTP server (the host webserver plus the SPA's static serving) with the browser talking Typert RPC over `/api` — already satisfies every desktop requirement except that it lives in a browser tab. Wrapping it as a distributed desktop program must not fork the client, weaken the loopback trust fence, or depend on the user's Node and pnpm.

## Decision

`apps/desktop` (`@deepseek-ai/dsh-desktop`, private) is a third product app beside `apps/cli` and `apps/web`, not a cordis plugin. The Electron main process spawns the dsh CLI as a sidecar — `node <dsh> --profile web --port 0` under a standalone Node binary bundled in `extraResources`, never Electron's own Node, whose version tracks Electron and not the repository's engines range (`^22.19 || >=24`). Readiness is the web app's existing stdout line `dsh web: http://127.0.0.1:<port>` (printed after plugin settlement), parsed from chunked stdout; the OS-picked port exists nowhere else, so no second health endpoint was added. The renderer is the unmodified SPA origin with the Electron sandbox on; off-origin navigations go to the OS browser. Teardown kills the process tree (POSIX group signals, Windows `taskkill /T /F`) at `will-quit`.

Staging assembly (`scripts/assemble-staging.mjs`) deploys `apps/desktop/deploy-root` — a dependency-only manifest generated by `scripts/generate-deploy-root.mjs` as the transitive closure over workspace dependency and peer edges, seeded from the dsh CLI's whole dependency face. The generated manifest is load-bearing: inside a pnpm deploy with injected workspace packages, one injected entry does not link its workspace-specifier dependencies and peers, so every workspace package the booted profiles import must be a DIRECT dependency of the deploy root. The deployed closure carries every built `lib/` and the SPA `dist/` (resolved at runtime through `require.resolve('@deepseek-ai/dsh-web-frontend/dist/index.html')` in the web-app bundle) and runs under plain Node with no pnpm state on the user machine. The standalone Node binary downloads from a mirror of the engines line and lands under `resources/node`, keyed to the packaging platform. `pnpm-workspace.yaml` overrides `@electron/get` to ≥3.1.0 because electron-builder 26.15.3 calls APIs missing from the 3.0.0 that the release-age policy would otherwise pin.

No session events, model inputs, or web transcripts change: the shell is a window and a process around the existing app, so the snapshot harness is unaffected and coverage is the unit tests over the pure logic (handshake parsing, teardown planning, path resolution) plus the staged-closure smoke in the assembly script.

## Alternatives considered

**Run the host inside the Electron main process.** Rejected: the harness requires the engines range, strict ESM, and native addons; coupling its boot to Electron's embedded Node and packaged-module layout makes every Electron upgrade a harness compatibility event for no user-visible gain.

**Tauri.** Rejected for now: the installer still needs a bundled Node for the sidecar, so the size win mostly cancels, while the repository gains a Rust toolchain and CI targets, and the Linux webkitgtk WebView adds a compatibility variable for the WebSocket downlink.

**A headless-static offline client.** Rejected: the browser trust fence and Typert RPC assume a local host process; removing it means a new remote-authenticated backend, i.e. a different product.
